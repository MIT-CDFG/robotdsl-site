Component library format ​

A component library is a directory the compiler is given with --library. It holds the physical parts a program assembles a robot from. The compiler reads two kinds of file from it, library.yaml and each part's component.yaml, and checks that the assets they name exist. It never opens a mesh, and it never reads the catalog, archive, or generated pages that a library repository may keep beside them. There is no install step and no default location.

This page is the schema. The library repository documents how parts are built; the compiler is the only implementation of what a declaration means.

Layout ​

text
<library>/
├── library.yaml                     name and the registered part ids
└── parts/<part-id>/
    ├── component.yaml               the declaration specified here
    ├── assets/                      meshes the declaration names
    └── ...                          README, LICENSE, CHANGELOG, images, source: not read

library.yaml ​

yaml
name: demo_parts          # an identifier
parts:                    # each id is parts/<id>/component.yaml
  - tslot_1515_drone
  - mecanum_black

A part that is not listed does not exist to the compiler. An id listed twice or without a declaration is a diagnostic; the other parts still load.

component.yaml ​

Values are YAML, read as JSON: only true and false are booleans, only null is null, and a plain scalar is a number when it spells a JSON number (1e-3 is a number here, unlike in YAML 1.1). A key given twice is a diagnostic. A key the schema does not list is a diagnostic; there are no free-form fields.

Every length is in metres, every angle in radians, every mass in kilograms, and every vector is [x, y, z] in the part's own frame: +X forward, +Y left, +Z up. Nothing is defaulted. A value the declaration does not state is absent, and a later phase that needs it reports what is missing rather than assuming.

yaml
schema_version: 1
id: mecanum_black                    # equals the directory name
category: wheel                      # chassis | wheel | sensor | attachment
description: Black 97 mm mecanum wheel.

visual:                              # the mesh that is shown
  file: assets/model.dae             # relative to the part directory
  xyz: [-0.0002, 0, -0.001]          # where the mesh sits in the part frame
  rpy: [0, 0, 1.57079]

wheel:                               # wheels only, and required for them
  radius: 0.0487                     # across the axle
  width: 0.0479                      # along the axle

inertial:
  mass: 0.09643
  origin_xyz: [0, 0, 0]              # centre of mass
  inertia: {ixx: 7.5613e-05, ixy: 0, ixz: 0, iyy: 7.5613e-05, iyz: 0, izz: 0.000114351}
  source: estimated                  # measured | datasheet | cad_measured | estimated | placeholder
  basis: solid cylinder at 270 kg/m^3   # how an estimate was chosen; required for estimated and placeholder

connectors:                          # mating points, at least one
  mount:
    pos: [-0.0013, 0.0011, 0]
    dir: [0, 0, 1]                   # mating axis, unit length
    joint: {type: continuous, axis: [0, 0, 1]}   # the joint created when mated; fixed when absent

profiles:                            # the component types the part can be used as
  Mecanum:
    mounts: {default: mount}         # logical mount name -> connector

Fields ​

FieldRequiredMeaning
schema_versionyes1
idyesThe part id; must equal the directory name
categoryyeschassis, wheel, sensor, or attachment
descriptionyesOne sentence for people

provenancenoname, manufacturer, source_url, license; each a string or null. license is an SPDX expression when known

Connectors ​

A connector is where another part mates. pos is the mating point, dir the mating axis: a wheel's axle, a mount's normal. Two parts mate with their dir vectors anti-parallel and their pos points coincident. up, when given, fixes the roll about dir for a part whose orientation matters (a camera lens, a lidar scan plane, a deck); it must be a unit vector perpendicular to dir. A rotation-symmetric part states no up.

joint is the joint that mating this connector creates: {type: fixed} (the default), or continuous, revolute, or prismatic with a unit axis. A wheel's axle connector carries continuous; a chassis mount carries nothing.

steering is stated by a chassis on a wheel mount that steers: {axis: [0, 0, 1], max_angle_rad: 0.6} is the kingpin's axis in the part frame and how far the wheel turns each way. Only a chassis may state it, and every mount a profile marks as steered (below) must. The compiler articulates the kingpin; the steering actuator and the knuckle body are the target's.

Profiles ​

A profile is one component type the part can be used as, named exactly as the vocabulary names the type, and maps the logical mount names of that type to the part's connectors. The Mecanum_four_wheel profile of a frame maps front_left_wheel, ..., and middle_top; a wheel's or a sensor's profile maps default. Two logical mounts may not share a connector. Which types exist and which mounts each needs is vocabulary, decided by the semantic phase, not by this format.

A chassis profile may add port_roles, mapping a logical mount to steered_drive or steered_free when that mount steers; the connector it maps to must then carry steering. Which mounts of a chassis type steer and which drive is vocabulary; the roles record what the part was built for.

Diagnostics ​

Every problem is a diagnostic in the library_load phase that points into the file. A problem with library.yaml itself blocks: nothing can be loaded. A part with any problem in its declaration is left out of the loaded library, so later phases never see a half-checked record, and the diagnostic is a warning that does not block a program which never names the part; a program that names such a part gets a name-resolution error that repeats why the part could not be loaded. A shared catalog with a few incomplete declarations thus still serves every program that uses its complete parts.

CodeCause
library.manifest_missingNo library.yaml at the given root (an environment failure: there is nothing to point at)
library.yaml_syntaxThe file is not valid YAML
library.duplicate_keyA key given twice; both occurrences are shown
library.invalid_keyA key that is not a plain name
library.unknown_fieldA key the schema does not list; the message lists the allowed ones
library.missing_fieldA required key is absent, or a wheel has no wheel block, or an estimate has no basis
library.wrong_typeA value of the wrong shape: not a mapping, not a number, not [x, y, z], ...
library.invalid_valueA value of the right shape but impossible: zero mass, a negative radius, an inertia tensor that violates the triangle inequality, an unknown category, an unknown joint type, a path that escapes the part directory
library.not_unit_vectorA dir, up, or joint axis that is not unit length (tolerance 0.001)
library.unsupportedA field that exists but is not valid for this part: collision on a wheel, wheel on a sensor, port_roles outside a chassis, an axis on a fixed joint
library.asset_missingvisual.file names a file that does not exist
library.id_mismatchid differs from the directory name
library.unknown_connectorA mount names a connector the part does not declare, or a port role names a mount the profile does not declare
library.duplicate_part, library.part_missingA part registered twice, or registered without a declaration

Not in this version ​

These are needed and not yet accepted; a declaration that contains them is rejected with library.unknown_field rather than silently ignored.

  • A part with internal links and joints (an arm, a pan-tilt mount, a suspension). Today a part is one rigid body and its connectors.
  • Shared interface types (interfaces/) that make two connectors compatible by declaration rather than by name.
  • The frame of a sensor part follows REP 103: it looks along its own +x axis, so a mount whose up is the chassis' +x makes a camera look forward.
  • Actuator and sensor specifications (torque and speed limits, field of view, range, rate, noise). The target still fills these in from its own defaults.
  • Source tags on values other than the inertial.
  • Assemblies and scene entities.

The facts are the same; the file moved and a few names changed. A converter belongs to the library repository.

From the previous format ​

The component library repository declared its parts for the previous compiler as <category>/<id>/part.yaml (schema_version: 3). tools/convert-library SOURCE DESTINATION writes such a checkout in this format: model becomes visual with the mesh copied under assets/, pos_local, dir_local and up_local lose their suffix, a wheel's geometry becomes wheel (its height is the width), the part's joint moves onto its connector, and estimate_basis becomes basis. Each profile is renamed to the component type it is (laser to Lidar, diff_four_wheel to Diff_drive, the arm, battery and circuit kinds to Attachment), and what the compiler never reads (images, catalog) is dropped. The converter invents nothing: a placeholder inertial without a basis, or a steered mount whose connector declares no kingpin, stays as it was and the loader reports it on the result. The report of the conversion names every value it dropped or could not carry.
