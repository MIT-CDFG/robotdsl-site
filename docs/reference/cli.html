Command line ​

text
mobiledsl compile FILE... [--library DIR]... [--check] [--target NAME] [--output DIR]
                  [--warnings-as-errors] [--json] [--color auto|always|never]
mobiledsl --version

A program is given as files: one .core, one .world, one .task, and optionally one .eval, in any order. The extension says which form a file is. There is no project file: the libraries, the target, and the output directory are settings of the compile, not of the program.

OptionMeaning
--library DIR, -l DIRA component library; repeat for several. A part must be in exactly one of them.
--checkStop after validation and emit nothing.
--target NAME, -t NAMEThe target to emit: ros-gz-nav2 or ros-mujoco-nav2. Needs --output.
--output DIR, -o DIRThe directory the target writes. It is created if missing; files of the same name are overwritten and other files are left alone. It must not be, hold, or sit inside a source file or a library.
--warnings-as-errorsA warning blocks compilation; each affected diagnostic says so in a note.
--jsonWrite the structured result to stdout.
--colorauto colors when stderr is a terminal and neither NO_COLOR nor TERM=dumb is set; always and never override.

Output ​

Diagnostics and one summary line go to stderr, in the form specified in Diagnostics. A clean check ends with Checked demo.core demo.world demo.task (9 checks), counting the validation rules that applied; a check that left a rule undecided says (9 checks, 1 undecided); a compile ends with Compiled demo.core demo.world demo.task (9 checks) into build (30 files); a failure ends with error: 1 error; ... did not compile.

text
error[name.unknown_component_type]: unknown component type 'Lidra'
  --> demo.core:11:5
   |
11 |     Lidra top_lidar(ref = "lidar_ld06", glue = (0, 0.0001, 0.0344, 0, 0, -1))
   |     ^^^^^ not a component type
   |
   = help: did you mean 'Lidar'?

error: 1 error; demo.core demo.world demo.task did not compile

With --json, stdout holds one document:

json
{
  "schema": "robotdsl.compile",
  "ok": true,
  "sources": ["demo.core", "demo.world", "demo.task"],
  "phases": {"source_load": "pass", "library_load": "pass", "parse": "pass", "...": "..."},
  "diagnostics": [],
  "validation": [{"rule": "assembly.glue_on_connector", "status": "pass", "evidence": ["..."]}]
}

When a target was written, the document also has output (the directory and the files written, compile.json included) and approximations (what the target stood in for, see the output contract).

phases names every compiler phase with pass, invalid, environment_failed, not_run (an earlier phase failed) or not_requested (--check stopped before it). diagnostics is the same list the terminal shows, in the JSON form. validation has one entry per rule with its status and evidence, including rules that were not_applicable.

Exit status ​

StatusMeaning
0Nothing blocked. Warnings may have been printed.
1A diagnostic blocked: a problem in the program or a library, a missing file, an unknown target, or a warning under --warnings-as-errors.
2The command line itself was wrong.

What a clean check does not establish ​

A clean check means the program names existing parts, every argument is well typed, every reference resolves, the assembly mates onto real connectors, and the standard rules pass on the facts the library states. It does not establish that the robot spawns, drives, or completes the task: those are observed when the emitted target runs, and the target reports them.
