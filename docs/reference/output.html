Output contract ​

A target turns the resolved program and its facts into the files a robot stack runs. This page fixes what every target's output guarantees, and then the files of the first target, ros-gz-nav2, of ros-mujoco-nav2, and of mjcf, the robot alone for MuJoCo.

Rules for every target ​

One directory, runnable by path. --output DIR receives an ordinary directory. The user builds nothing and installs nothing to run it; the entry point is a launch file inside it, or for mjcf the model MuJoCo opens. A file of the same name is replaced, never written through, so a link in its place is replaced and its target left alone; other files in the directory are left alone. The compiler refuses an output directory that is, or contains, a source file or a library, and a directory inside it that is a symbolic link (environment.output_linked).

One authoritative file per fact. A fact appears in the one file whose consumer needs it, and every other file that needs the same fact is derived from the same analysis value at compile time, never re-derived at run time. The table in each target's section says which file owns which fact.

No absolute paths. A file on disk never contains the output directory's path, so the directory can be moved or mounted elsewhere. Where a consumer demands an absolute path at run time (a simulator plugin that opens a parameter file by name), the file holds the token ${OUTPUT_DIR} and the launch file substitutes the real path when it starts the process.

Deterministic. The same program, libraries and compiler version produce byte-identical output: no timestamps, no host names, no random ids.

Execution input and inspection output are separate. The runtime reads only the files under robot/, world/, nav/, task/, launch/ and runtime/, and of the mjcf target's output only scene.xml and drive.json. compile.json is for people and tools: the facts, the validation results, the approximations the target made, and the sources and parts the output came from. Deleting it changes nothing at run time.

Approximations are declared. Where the target stands in for something it cannot simulate as such (a mecanum wheel as a sphere with anisotropic friction, a lidar with a default sample count), it says so in compile.json under approximations, with what was approximated, how, and why. Nothing is approximated silently, and nothing the target cannot do is emitted as if it could: an unsupported construct is a target.* diagnostic that stops emission.

The task stays goal-agnostic in the tree and goal-bound in the mission. The behavior tree names what to do; the mission file holds the poses the tree's goals resolve to. A target's own executor reads both.

ros-gz-nav2 ​

ROS 2 Jazzy, Gazebo Harmonic, ros2_control, and Nav2. The output is:

Nav2 reads parameter files in order with later files winning, so the launch file passes nav2.base.yaml then nav2.robot.yaml. Everything the robot decides is in the second file and nowhere else.

Status. Every file above is emitted. The launch brings up the simulator, the robot, the drive controller, Nav2 and the task runtime, in that order, and shuts everything down when the task ends (exit_on_task_end:=false keeps it running; navigation:=false brings up only the simulator, the robot and its drive controller, to drive it by hand on /cmd_vel). It also ends the run, and says what stopped, when a process the base is driven through ends before the launch does: the runtime's drive node, or the bridge, through which the controllers get the clock a command's lifetime is measured on. Nothing after these ends a command, so a base whose drive had stopped would run on at its last speeds; a run ended this way writes no result. Gazebo itself takes about five seconds to end. The task runtime writes run/task_result.json under the output directory (run_dir:=DIR moves it); run/ is never written by the compiler, so a rerun of the compiler leaves it alone. Navigation has no map and no localization yet: the world frame map meets odom at the spawn pose through a static transform, and both costmaps are filled by the laser alone.

Frames and topics ​

  • base_footprint is the root link: the ground projection of the robot, the frame the spawn pose places, and the controller's base frame. base_link is the chassis part frame; every other link is named after its component and its joint <component>_joint, and hangs from the link of the part it is mated onto: a wheel from its motor, a motor from the chassis. A wheel joint carries the limits its motor's part states, its stall torque as the effort and its no-load speed as the velocity. A wheel that a motor turns through a driveline of the chassis hangs from the chassis; its joint carries the motor's speed over the driveline's reduction and an equal share of its torque times the reduction, or no limit when the driveline states none. A track's unit is a fixed link whose one collision is the box of its belt: as long as the belt's run on the ground and as wide as the belt, standing on the run, as tall as a wheel that travels as far per turn as the belt. No joint and no further link is made for a belt.
  • The base takes geometry_msgs/msg/TwistStamped on /cmd_vel, whatever the controller; it publishes odometry on /odom and odom -> base_footprint on /tf. A stale command (older than 0.5 s) stops the base. Mecanum, two-wheel differential, skid-steer, tricycle, Ackermann and omni bases are bound to the matching ros2_control controllers; the part on a steered mount, a motor or a free wheel, hangs from a kingpin joint named <component>_steer_joint, and wheels that only roll are observed but not commanded. Every wheel the program drives is commanded: a binding that left one out is refused. An omni base is bound to velocity_controllers/JointGroupVelocityController, and runtime/run_omni_drive.py turns /cmd_vel into the wheel speeds from each wheel's position and rolling direction (robot/omni_drive.json) and publishes the odometry from the measured wheel speeds; ros2_controllers' omni controller models only wheels evenly spaced on a circle, and the catalog's four-wheel omni bases sit on rectangles. An Ackermann base is bound to the same velocity group for its driven wheels, two or four, and to position_controllers/JointGroupPositionController, spawned as steering_controller, for its kingpins; runtime/run_steering_drive.py turns /cmd_vel into each driven wheel's speed along its own circle about the turning centre and each kingpin's angle (robot/steering_drive.json), and publishes the odometry from the rear wheels' measured speeds. ros2_controllers' Ackermann controller takes exactly two traction joints. A tracked base has no joint, so the description holds no <ros2_control> block, robot/controllers.yaml is not written and the launch starts no controller manager and spawns no controller. runtime/run_track_drive.py holds /cmd_vel to what the two belts' motors reach, each belt running at the speed of its side, a half separation from the chassis' origin (robot/track_drive.json); it publishes the motion the belts then carry the base in on /tracks/cmd_vel (geometry_msgs/msg/Twist) and the odometry that motion stands for. The bridge hands that topic to Gazebo's TrackedVehicle system, which tells the TrackController on each belt's link its speed and the point the base turns about; a belt stops when nothing has reached it for 0.5 s. A chassis whose origin does not lie midway between its two tracks, within 2 mm, is refused.
  • A base that steers plans with Smac Hybrid-A* at its minimum turning radius and follows with MPPI's Ackermann model; it is not held to a final heading, since it cannot turn in place to fix one. The radius is the tightest circle the middle of the unsteered axle follows with every kingpin within its limit: for each kingpin, its distance ahead of that axle over the tangent of its limit, plus its distance from the centre line.
  • Sensors publish under their role name: the first laser on /scan, the first spinning lidar on /lidar3d/scan (its middle ring) and /lidar3d/points, the first IMU on /imu, the first camera on /camera/image_raw and /camera/camera_info, the first depth camera on /depth/image_raw and /depth/points, the first RGBD camera on /rgbd/image_raw, /rgbd/depth/image_raw, /rgbd/points and /rgbd/camera_info, the first ultrasonic range finder on /ultrasonic/range (its cone of beams on /ultrasonic/points), the first range finder that measures with light (Range) on /range (its cone on /range/points), the first bumper on /bumper (ros_gz_interfaces/msg/Contacts); a second sensor of a kind is suffixed with its component name. Frames are the component names.
  • The costmaps' footprint is the box of the robot's collision shapes: the analysis footprint, widened to each wheel's sphere (below), which reaches further across the axle than the wheel's width.
  • The costmaps mark what every point cloud sees, points 0.05 to 2 m above the ground, and with the localizer read one scan. It is the first laser's; without a laser it is the first spinning lidar's middle ring; a robot with neither but with a depth or RGBD camera gets /scan from runtime/run_depth_scan.py, which projects the cloud onto the ground plane in base_footprint (points 0.05 to 2 m high, within 5 m, 360 beams, beams outside the camera's view infinite). Range finders feed the costmaps' range layer: runtime/run_range_sensor.py reports each cone's nearest return as a sensor_msgs/msg/Range, ULTRASOUND or INFRARED, and a reading at the maximum range clears the cone. An ultrasonic sensor's returns less than 0.05 m above the ground are dropped first (every simulated beam returns, a pulse glancing off the floor does not); a Range sensor keeps them, since light comes back from the floor. A Range sensor whose limits are equal says only whether something is within that distance: it reports -inf or +inf, and the range layer marks or clears its cone. A robot with no range sensor is warned that it navigates blind.
  • The simulator publishes the model pose on /model/<robot>/pose as tf2_msgs/msg/TFMessage. Tests and the evaluator judge a run by this, never by odometry.

What the launch file substitutes at run time ​

  • ${OUTPUT_DIR} in robot/robot.urdf (the path of controllers.yaml for gz_ros2_control, and the mesh paths). world/world.sdf holds nothing to substitute: it names an object's mesh by its path from the world file, meshes/<object-id>/<file>, which Gazebo resolves against that file.
  • The path of nav/map.yaml, passed to the map server.
  • The spawn pose, read from task/mission.json, for the simulator and, on a robot without a laser, for the map -> odom transform.

Nothing else is computed at launch; the launch file is a fixed program over the files above. Nav2's own default behavior tree runs Navigate; the program's tree is not handed to bt_navigator.

The task ​

task/behavior_tree.xml is the task in BehaviorTree.CPP's XML layout with the language's node names as tags and its parameter names as attributes, so it reads like the program and opens in Groot. A goal is written by name (<Navigate goal="dock"/>) and resolved through task/mission.json, which holds every goal and every entity, since Navigate and GoalReached take either. A task whose body has several nodes runs them in order, so the body is wrapped in a Sequence.

runtime/run_task.py runs the tree. It needs ROS 2 and, when the tree uses Navigate, Spin, Advance or BackUp, the task waits for a Nav2 costmap or the runtime starts Nav2's servers, the nav2_msgs package; nothing from the compiler. Each leaf is bound as follows.

NodeBound to
NavigateNav2 navigate_to_pose, goal in the map frame
SpinNav2 spin
Advance, BackUpNav2 drive_on_heading, backup; 0.15 m/s unless speed_mps is given
Strafe/cmd_vel with odometry feedback (Nav2 has no lateral behavior)
Waitsimulation time
Stopzero velocity on /cmd_vel for half a second

DistanceTraveledodometry path length since the task started
TimeExpiredsimulation time since the task started

The launch starts Nav2's lifecycle manager without autostart. The task runtime asks it to start the servers, 3 s of wall time or more after the manager first answered it (run_task.py --start-lifecycle, --start-after), and waits until the manager reports them active. The manager answers once it has made its clients of the servers, and the wait gives the servers more time to discover those clients. rmw_fastrtps gives a server's reply up when the manager's client has not matched it within the time the reply may block, and Nav2 Jazzy's manager waits for a change_state reply without a limit. The 3 s are a measured remedy, not a guarantee. After a start that failed the manager reports its servers not active, so the task does not start. When the runtime receives the manager's answer that it could not start its servers, the run ends with status not_started and says so, without waiting for the limit below.

The task starts once the drive's odometry and the robot's pose in the map have arrived, Nav2's lifecycle manager reports its servers active, and the task has received from the local and the global costmap their map and the robot's footprint, which Nav2 checks a goal against (so that Nav2's servers most likely have them too); one that cannot start within 120 s of simulation time ends with status not_started and says what it waited for. The tree ticks at ten hertz. The mission's timeout_s ends the run with status timeout. run/task_result.json records the status (success, failure, timeout, error, not_started), the start and end times, one event per leaf with its parameters and outcome, the final pose the robot believes it has, and the odometry distance. It is the robot's own account. A halted Nav2 action is canceled at once, and before the run is judged the runtime waits up to 5 s for the goal to stop; a goal that has not stopped by then is named in unstopped_actions.

The evaluation ​

While the task runs, the runtime records the robot's pose as the simulator publishes it, the joint states, and every bumper's contact reports. When the task ends it writes run/evaluation.json with three verdicts that rest on different evidence:

  • task: the status the task runtime reported.
  • physical: from the recorded ground truth alone. Whether the robot ended near the last goal it navigated to (within twice the controller's goal tolerance, since the controller stops on its belief and the ground truth differs from it by the localization error), and its closest approach to any Obstacle over the run; touching one (within 5 mm) fails.
  • checks: each check of the .eval file, pass, fail or unknown, with the value it was judged on. Check_vel, Check_acc, Check_jerk and Check_effort read the joint states of the named wheel and judge every sample by magnitude; Check_distance and Check_clearance use the recorded poses and the planar shapes of task/evaluation.json; Check_contact on a Bumper reads the bumper's own reports (the seconds it was pressed and the scene entities that pressed it), on any other part the poses and shapes; Check_time uses the task's duration. The vocabulary states what each bound means.

The shapes are the collision geometry the robot is simulated with, seen from above: the chassis and sensor collision boxes, each wheel and each ground contact a part declares as a circle of its radius (both are spheres in the simulator), a part without a collision box as a point, and each scene entity as the regions its shapes cover seen from above at its full pose, so that a cylinder lying on its side covers its length: one region for a primitive, and for a library object one for each shape it collides by, a robot being as near to it as to the nearest of them. An object that declares no collision has no region and is not listed. The map is drawn from the same regions. A part's ground contacts count as that part: a check on the chassis also measures the skid under it. Nothing is read from odometry or from Nav2. A check on a part without a moving joint is refused at compile time; a check that has no samples to judge is unknown, never pass.

Not emitted ​

A program that uses any of these stops with a target.unsupported diagnostic naming the construct, and nothing is written: an omni base whose rolling directions do not span the plane, a steering base whose chassis declares no kingpin, a scene entity declared movable (is_static = false: an entity states no mass to move it with), a joint check on a part without a moving joint (a track among them: its belt is a moving surface), a part with links of its own, which no target writes yet, a moving joint (revolute, prismatic or continuous) on a connector a mating uses, other than a wheel's own: on the mating part's own connector unless the part is a wheel, or on the connector it mates onto, either of which the robot description would hold fixed, a track whose part states no travel per turn or whose run does not lie along the robot, a tracked base whose tracks do not lie equally far to the two sides of its chassis' origin, a component named like a link the target adds: base_footprint, base_link, a declared ground contact's <link>_contact_<n> or a steered wheel's knuckle <wheel>_steer, and a scene entity named like another model of the world: the robot, or ground_plane when the scenario has a floor.

The ros-mujoco-nav2 target ​

The second target keeps everything above that is ROS: the robot description (robot/robot.urdf, with a <mujoco> compiler block MuJoCo's URDF reader takes and none of Gazebo's blocks), the controllers, the navigation parameters, the map, the task files and the runtime, and swaps the simulator. Its world/ holds mujoco.json instead of an SDF and a bridge: the ground, the world's light (the Gazebo world's, below), the scene entities (each a body <name>::link, so that no entity name can meet a link's in MuJoCo's single namespace, with its shapes: the primitive a program states, or the shapes a library object collides by, each placed in the entity's frame; and for a library object drawn in glTF its visual, the mesh's file in the output and where it sits in the entity's frame, the mesh lying under world/meshes/<object-id>/ as in the Gazebo target), the actuators on the wheel and kingpin joints, a tracked base's belts and the topic their motion arrives on, the wheels' contact friction, the sensors with the topics they publish on, and the spawn pose. Each body weighs what the library's inertial states: the compiler block stops MuJoCo from inferring a mass from a link's collision shapes, so a link without an inertial (the root, a ground contact's) weighs only MuJoCo's 1 g bound. runtime/run_mujoco_sim.py loads the description and that scene, steps the physics paced to the wall clock, publishes /clock, and speaks to ros2_control through its topic-based hardware (/mujoco/joint_states, /mujoco/joint_commands). It publishes the robot's pose on /model/<robot>/pose and every sensor on the same topics as the Gazebo target, computed from the physics state: lasers and range finders cast rays, which return from what collides (the robot never sees itself, and the floor returns only to a Range sensor, which measures with light), cameras render offscreen (OSMesa by default, MUJOCO_GL=egl with a GPU) what is shown: the sky, the floor and each entity, by its shape or by its object's mesh, a mark that only shows among them, and never the robot's own collision shapes. A camera draws from the near end of its range to the far end and shows the sky beyond, as a Gazebo camera does, also in the colour picture of a camera that measures depth. The far end of a camera that measures depth is a distance from it, 5 m, and that of a plain camera a distance ahead of it, 10 m, as in Gazebo; an IMU reads the body's motion, a bumper reads the contacts. The launch takes the same arguments; headless has no effect.

Both targets light a world alike, since a program states no light: an ambient light of 0.4, a sun of 1 that shines along (-0.5, 0.1, -0.9) and casts shadows, a sky of (0.7, 0.75, 0.85), a floor of 0.8 grey and, for a box, a sphere or a cylinder a program states, a grey of 0.5. world/world.sdf states them as they are. Gazebo encodes its picture, each value raised to 1 / 2.2, and MuJoCo draws the numbers it is given, so world/mujoco.json holds the colours encoded (background, ground, shape, and gamma for the node to encode a mesh's material colours by) and the sun at half its strength, at which the robot's colour camera read one world alike in the two test images: the sky (217, 223, 235) and (214, 221, 234) of 255, the lit floor 188 to 209 and 196, a picture's red (76, 5, 8) and (79, 14, 15), a stated box's side away from the sun 71 and 74. The node draws the sun's shadows in four times the depth MuJoCo would, since the lit floor showed dark specks short of the horizon otherwise.

The node runs on MuJoCo 3.11 or later and says so on an older one. A tracked base is simulated through the surface velocity of a geom, which MuJoCo has had since 3.11: the node takes the motion on /tracks/cmd_vel and moves the surface of each belt's box as that motion requires at every point of it, along the run at the speed of its side and across it as the turn swings the point round, so that what touches the floor stands still on it. No controller manager runs for such a base.

The launch ends the run, and says what stopped, when the runtime's drive node or the controller manager ends before it does: a group controller holds the last command its drive gave it, and the MuJoCo node the last one the controller manager gave it.

A geom's friction in MuJoCo is the same in every direction, and the node writes no contact pairs, so a sphere cannot stand in for a mecanum or omni wheel, which slides freely across its rolling direction on its rollers: a base on such wheels is refused with target.unsupported and compiles for ros-gz-nav2 instead (the mjcf target writes a mecanum wheel as its rollers). A part that declares neither a collision box nor a hull is refused too, unless it is a wheel, which collides as a sphere of its radius, or a track, which collides as its belt's box: the Gazebo target collides such a part through its visual mesh, which the library ships as Collada, and MuJoCo reads meshes only as STL, OBJ or MSH. A library object that only shows, by a mesh that is not glTF, is refused as well: the node reads glTF and nothing else of a world's objects, and nothing of this one would be in the scene. The world's gravity and ground plane are the program's, as in Gazebo, and so is the refusal of an entity declared movable. A library environment is in neither target's files as such: its entities are the scenario's own by the time a target reads the world. Its own stand-ins, declared in compile.json:

The test image is robotdsl/ros-mujoco-nav2:jazzy, built from docker/ros-mujoco-nav2/jazzy/Dockerfile.

The mjcf target ​

The third target writes the robot alone, for MuJoCo without ROS: the model MuJoCo opens by itself, its viewer or MuJoCo compiled to WebAssembly in a browser page, and what drives it. It is the robot to drive by hand.

FileWhat it holds
scene.xmlThe robot on its floor as one MJCF, which names no file
drive.jsonHow a base motion becomes each actuator's command or each belt's surface motion, and which body each component is

scene.xml is the robot ros-mujoco-nav2 gives MuJoCo, as MuJoCo's URDF reader makes the robot description into a model under that target's compiler block, written out: a body for each link where its joint puts it, a hinge for each continuous or revolute joint, bounded in force by its limit's effort, each body's inertial as the robot description gives it, the steering knuckles it adds included, within MuJoCo's bounds on mass and inertia, and each collision as a geom, a declared hull as a mesh written in the model with its faces wound outward, as its STL has them. Around it is what that target's node adds at run time: a free joint at the world's spawn pose, the robot's geoms in group 1, which meet the world and not each other, the friction of each wheel, belt and ground contact, the world's gravity and its floor, the step of 1 ms, the implicit-fast integrator, a velocity actuator on each joint the drive turns and a position actuator on each kingpin it steers, named <joint>_actuator, and the node's lighting: its headlight, its sun, its sky and the depth of the sun's shadows. Of the world there is the floor and the gravity and nothing else; a sensor is its body, mass and collision, without its sensing; nothing of ROS, Nav2 or the task.

The tests build the model both ways, by this target and by that target's own node from its output, and compare in MuJoCo 3.15 every field of their bodies, joints, degrees of freedom, geoms, actuators, light and sky, their options and their drawing settings. Set aside are the world's entities, the cameras the node adds for the robot's sensors and the nearest distance it has them draw at, the light's offset from the world's centre of mass, which the entities weigh in, and the offsets that place an element in its model's arrays: of these, each body's parent, each joint's and each geom's body and each actuator's joint are compared by name, and the others, which MuJoCo derives from them, are left out. A mesh is compared by its triangles and their normals in its body's frame, since MuJoCo keeps a mesh in a frame it chooses by its shape. They agree for a robot with at most one hull part. With two, that target's model collides every hull part by the first one's mesh: MuJoCo's URDF reader names a mesh by its file's name, which is collision.stl for every hull.

A mecanum wheel, which ros-mujoco-nav2 refuses, is written as its rollers: its body is the hub, with no shape of its own, and round it are its rollers, each turning freely on a hinge about its own axis that nothing drives. The roller under the hub lies at 45 degrees to the axle, on whichever of the two such lines the mount's roller axis as ros-gz-nav2 states it is nearer (seen from above, (1, -1) at the front-left and rear-right mounts, (1, 1) at the other two), and the others follow it round. A roller is a barrel, as a mecanum wheel's are: five spheres along its axis, each reaching the wheel's radius from the axle, so that the rollers keep to the wheel's radius but for the dips between their spheres. At its middle a roller's radius is a quarter of the wheel's radius or of the rollers' span, whichever is less; the rollers span 95% of the wheel's width along the axle; and there are as many as make their spans overlap round the rim by a tenth, twelve at the least. A wheel is refused whose rollers' end spheres would be less than a fifth of their middle radius (a wheel wider than about two thirds of its diameter, 0.666 of it), or that would need more than 32 rollers (one narrower than about a ninth of it, 0.108). Each roller weighs 1 g with a moment of 1e-6 kg m² about each axis, the least the compiler block takes, out of the wheel's mass; a wheel whose hub would be left less than 1 g is refused. The hub keeps the rest of the mass and the part's inertia, so the wheel turns about its axle a little heavier than the part states. The rollers meet the floor with a rolling wheel's friction, and not the robot; each roller's body and hinge are named <wheel's link>/roller_<n>, a name no component can have.

drive.json (robotdsl.mjcf_drive) names, by bodies, the body whose frame is each component's own (base_link for the chassis), and says how to drive the base:

  • "kinematics": "differential" (Diff_two_caster, Diff_drive), as ros-mujoco-nav2's diff_drive_controller drives it: each driven wheel turns at (v - w·y) / radius, its y half the wheel separation on the left and minus it on the right.

  • "kinematics": "steering" (Ackermann, Tricycle): the runtime's steering drive (runtime/mobiledsl_runtime/steering_kinematics.py in the ROS targets' output), from axle_x, min_turning_radius, the driven wheels (x, y, offset, radius) and the kingpins (x, y, limit, sign): each driven wheel at the speed of its own path about the turning centre and each kingpin at its own angle, the turn held to what the kingpins can steer. That is how ros-mujoco-nav2 drives a car. It drives a tricycle by tricycle_controller, which takes the front wheel on its kingpin's axis; here a tricycle is driven as a car is, a stand-in declared below.

  • "kinematics": "holonomic" (Mecanum_four_wheel), as ros-gz-nav2's mecanum_drive_controller drives it: each driven wheel turns at its coupling row times (v, v_left, w), the base's speed ahead and to the left (m/s) and its turn to the left (rad/s). The rows are the controller's, for wheels of radius r whose mounts lie a lever arm k (half the wheelbase plus half the track) from the middle along x and y: (1, -1, -k) / r front left, (1, 1, k) / r front right, (1, 1, -k) / r rear left and (1, -1, k) / r rear right.

  • "kinematics": "tracks" (Tracked), as ros-mujoco-nav2's node drives it. No joint turns: the surfaces of the belts' boxes move.

    • Once, with the model as it loads and mj_kinematics run on it, take every geom of each of the belts' bodies (body): body_geomnum of them from body_geomadr. Keep each one's centre in the frame of the root body, c = R_rootᵀ (x_geom - x_root), and the rotation from that frame into its own, R_geomᵀ R_root. Tell MuJoCo that surfaces move (flg_surfacevel), which it skips otherwise, before stepping.
    • For a base motion v (m/s) and w (rad/s), take one factor s: the least max_speed / |v - w*c_y| over the geoms of the belts that state a max_speed (m/s), where that is less than 1, and otherwise 1. A null max_speed bounds nothing.
    • With v' = sv and w' = sw, each geom's geom_surfacevel is the linear velocity (-v' + w'*c_y, -w'*c_x, 0) in its components 0 to 2 and the angular velocity (0, 0, -w') in 3 to 5, each rotated into the geom's frame.

    That is the runtime's surface_motion (runtime/mobiledsl_runtime/track_kinematics.py in the ROS targets' output), as the node applies it to each command; the node also drops a command that is not finite, and stops the belts when commands stop arriving.

Each driven wheel and kingpin names its actuator and joint; a wheel's max_speed is its motor's no-load speed at the wheel's joint, through whatever reduction the drive has between them, in rad/s, which bounds the joint's velocity command; null where the part states none.

It refuses, as ros-mujoco-nav2 does, a base on omni wheels, a part with links of its own, which no target writes yet, a moving joint on a connector a mating uses other than a wheel's own, and a robot with a part that declares neither a collision box nor a hull, other than a wheel, which collides as a sphere of its radius, and a track, which collides as its belt's box: such a part would collide through its visual mesh. Of its own it refuses a world without a floor, and a mecanum wheel too light for its rollers, whose hub would be left less than 1 g, and one too wide or too narrow for them. Its stand-ins, in compile.json, are that target's for the wheels, the tracks, the ground contacts and the drive, but for the odometry a tracked base's drive makes there, which this target makes none of; with these of its own:
