Output contract ​

A target turns the resolved program and its facts into the files a robot stack runs. This page fixes what every target's output guarantees, and then the files of the first target, ros-gz-nav2.

Rules for every target ​

One directory, runnable by path. --output DIR receives an ordinary directory. The user builds nothing and installs nothing to run it; the entry point is a launch file inside it. A file of the same name is replaced, never written through, so a link in its place is replaced and its target left alone; other files in the directory are left alone. The compiler refuses an output directory that is, or contains, a source file or a library, and a directory inside it that is a symbolic link (environment.output_linked).

One authoritative file per fact. A fact appears in the one file whose consumer needs it, and every other file that needs the same fact is derived from the same analysis value at compile time, never re-derived at run time. The table in each target's section says which file owns which fact.

No absolute paths. A file on disk never contains the output directory's path, so the directory can be moved or mounted elsewhere. Where a consumer demands an absolute path at run time (a simulator plugin that opens a parameter file by name), the file holds the token ${OUTPUT_DIR} and the launch file substitutes the real path when it starts the process.

Deterministic. The same program, libraries and compiler version produce byte-identical output: no timestamps, no host names, no random ids.

Execution input and inspection output are separate. The runtime reads only the files under robot/, world/, nav/, task/, launch/ and runtime/. compile.json is for people and tools: the facts, the validation results, the approximations the target made, and the sources and parts the output came from. Deleting it changes nothing at run time.

Approximations are declared. Where the target stands in for something it cannot simulate as such (a mecanum wheel as a sphere with anisotropic friction, a lidar with a default sample count), it says so in compile.json under approximations, with what was approximated, how, and why. Nothing is approximated silently, and nothing the target cannot do is emitted as if it could: an unsupported construct is a target.* diagnostic that stops emission.

The task stays goal-agnostic in the tree and goal-bound in the mission. The behavior tree names what to do; the mission file holds the poses the tree's goals resolve to. A target's own executor reads both.

ros-gz-nav2 ​

ROS 2 Jazzy, Gazebo Harmonic, ros2_control, and Nav2. The output is:

text
<output>/
├── robot/
│   ├── robot.urdf            links, joints, inertials, visuals, collisions,
│   │                         ros2_control interfaces, Gazebo sensor and friction blocks
│   ├── controllers.yaml      controller_manager, the drive controller, joint states
│   └── meshes/<part-id>/     the visual meshes, copied from the libraries
├── world/
│   ├── world.sdf             physics, lighting, ground plane, scene entities
│   └── bridge.yaml           ros_gz_bridge topics: clock, sensors
├── nav/
│   ├── nav2.base.yaml        plugin choices and constants
│   ├── nav2.robot.yaml       what the robot decides: footprint, inflation, kinematics, AMCL start
│   ├── map.pgm               the occupancy grid drawn from the world's obstacles
│   └── map.yaml              its resolution and origin, for the map server
├── task/
│   ├── behavior_tree.xml     the task as a BehaviorTree.CPP tree over the vocabulary's actions
│   ├── mission.json          every goal and entity by name, the spawn, the time budget
│   └── evaluation.json       the checks, and the planar shapes of the parts and entities
├── launch/
│   └── bringup.launch.py     the entry point: simulator, robot, controllers, navigation, task
├── runtime/                  the task executor and its adapters, copied here; needs only ROS 2
└── compile.json              inspection: facts, validation, approximations, provenance

Nav2 reads parameter files in order with later files winning, so the launch file passes nav2.base.yaml then nav2.robot.yaml. Everything the robot decides is in the second file and nowhere else.

Status. Every file above is emitted. The launch brings up the simulator, the robot, the drive controller, Nav2 and the task runtime, in that order, and shuts everything down when the task ends (exit_on_task_end:=false keeps it running; navigation:=false brings up only the simulator, the robot and its drive controller, to drive it by hand on /cmd_vel). The task runtime writes run/task_result.json under the output directory (run_dir:=DIR moves it); run/ is never written by the compiler, so a rerun of the compiler leaves it alone. Navigation has no map and no localization yet: the world frame map meets odom at the spawn pose through a static transform, and both costmaps are filled by the laser alone.

Frames and topics ​

  • base_footprint is the root link: the ground projection of the robot, the frame the spawn pose places, and the controller's base frame. base_link is the chassis part frame; every other link is named after its component and its joint <component>_joint.
  • The base takes geometry_msgs/msg/TwistStamped on /cmd_vel, whatever the controller; it publishes odometry on /odom and odom -> base_footprint on /tf. A stale command (older than 0.5 s) stops the base. Mecanum, two-wheel differential, skid-steer, tricycle, Ackermann and omni bases are bound to the matching ros2_control controllers; a steered wheel hangs from a kingpin joint named <component>_steer_joint, and wheels that only roll are observed but not commanded. An omni base is bound to velocity_controllers/JointGroupVelocityController, and runtime/run_omni_drive.py turns /cmd_vel into the wheel speeds from each wheel's position and rolling direction (robot/omni_drive.json) and publishes the odometry from the measured wheel speeds; ros2_controllers' omni controller models only wheels evenly spaced on a circle, and the catalog's four-wheel omni bases sit on rectangles.
  • A base that steers plans with Smac Hybrid-A* at its minimum turning radius (wheelbase over the tangent of the steering limit) and follows with MPPI's Ackermann model; it is not held to a final heading, since it cannot turn in place to fix one.
  • Sensors publish under their role name: the first laser on /scan, the first spinning lidar on /lidar3d/scan (its middle ring) and /lidar3d/points, the first IMU on /imu, the first camera on /camera/image_raw and /camera/camera_info, the first depth camera on /depth/image_raw and /depth/points, the first RGBD camera on /rgbd/image_raw, /rgbd/depth/image_raw, /rgbd/points and /rgbd/camera_info, the first ultrasonic range finder on /ultrasonic/range (its cone of beams on /ultrasonic/points), the first bumper on /bumper (ros_gz_interfaces/msg/Contacts); a second sensor of a kind is suffixed with its component name. Frames are the component names.
  • The costmaps' footprint is the box of the robot's collision shapes: the analysis footprint, widened to each wheel's sphere (below), which reaches further across the axle than the wheel's width.
  • The costmaps mark what every point cloud sees, points 0.05 to 2 m above the ground, and with the localizer read one scan. It is the first laser's; without a laser it is the first spinning lidar's middle ring; a robot with neither but with a depth or RGBD camera gets /scan from runtime/run_depth_scan.py, which projects the cloud onto the ground plane in base_footprint (points 0.05 to 2 m high, within 5 m, 360 beams, beams outside the camera's view infinite). Range finders feed the costmaps' range layer: runtime/run_range_sensor.py reports each cone's nearest return more than 0.05 m above the ground as a sensor_msgs/msg/Range (every simulated beam returns, a pulse glancing off the floor does not), and a reading at the maximum range clears the cone. A robot with no range sensor is warned that it navigates blind.
  • The simulator publishes the model pose on /model/<robot>/pose as tf2_msgs/msg/TFMessage. Tests and the evaluator judge a run by this, never by odometry.

What the launch file substitutes at run time ​

  • ${OUTPUT_DIR} in robot/robot.urdf (the path of controllers.yaml for gz_ros2_control, and the mesh paths).
  • The path of nav/map.yaml, passed to the map server.
  • The spawn pose, read from task/mission.json, for the simulator and, on a robot without a laser, for the map -> odom transform.

Nothing else is computed at launch; the launch file is a fixed program over the files above. Nav2's own default behavior tree runs Navigate; the program's tree is not handed to bt_navigator.

The task ​

task/behavior_tree.xml is the task in BehaviorTree.CPP's XML layout with the language's node names as tags and its parameter names as attributes, so it reads like the program and opens in Groot. A goal is written by name (<Navigate goal="dock"/>) and resolved through task/mission.json, which holds every goal and every entity, since Navigate and GoalReached take either. A task whose body has several nodes runs them in order, so the body is wrapped in a Sequence.

runtime/run_task.py runs the tree. It needs ROS 2 and, when the tree uses Navigate, Spin, Advance or BackUp, the nav2_msgs package; nothing from the compiler. Each leaf is bound as follows.

NodeBound to
NavigateNav2 navigate_to_pose, goal in the map frame
SpinNav2 spin
Advance, BackUpNav2 drive_on_heading, backup; 0.15 m/s unless speed_mps is given
Strafe/cmd_vel with odometry feedback (Nav2 has no lateral behavior)
Waitsimulation time
Stopzero velocity on /cmd_vel for half a second
GoalReachedmap -> base_footprint within the goal tolerance of nav2.base.yaml
DistanceTraveledodometry path length since the task started
TimeExpiredsimulation time since the task started

The tree ticks at ten hertz. The mission's timeout_s ends the run with status timeout. run/task_result.json records the status (success, failure, timeout, error, not_started), the start and end times, one event per leaf with its parameters and outcome, the final pose the robot believes it has, and the odometry distance. It is the robot's own account. A halted Nav2 action is canceled at once, and before the run is judged the runtime waits up to 5 s for the goal to stop; a goal that has not stopped by then is named in unstopped_actions.

The evaluation ​

While the task runs, the runtime records the robot's pose as the simulator publishes it, the joint states, and every bumper's contact reports. When the task ends it writes run/evaluation.json with three verdicts that rest on different evidence:

  • task: the status the task runtime reported.
  • physical: from the recorded ground truth alone. Whether the robot ended near the last goal it navigated to (within twice the controller's goal tolerance, since the controller stops on its belief and the ground truth differs from it by the localization error), and its closest approach to any Obstacle over the run; touching one (within 5 mm) fails.
  • checks: each check of the .eval file, pass, fail or unknown, with the value it was judged on. Check_vel, Check_acc, Check_jerk and Check_effort read the joint states of the named wheel and judge every sample by magnitude; Check_distance and Check_clearance use the recorded poses and the planar shapes of task/evaluation.json; Check_contact on a Bumper reads the bumper's own reports (the seconds it was pressed and the scene entities that pressed it), on any other part the poses and shapes; Check_time uses the task's duration. The vocabulary states what each bound means.

The shapes are the collision geometry the robot is simulated with, seen from above: the chassis and sensor collision boxes, each wheel and each ground contact a part declares as a circle of its radius (both are spheres in the simulator), a part without a collision box as a point, and each scene entity as the region its shape covers seen from above at its full pose, so that a cylinder lying on its side covers its length. The map is drawn from the same regions. A part's ground contacts count as that part: a check on the chassis also measures the skid under it. Nothing is read from odometry or from Nav2. A check on a part without a moving joint is refused at compile time; a check that has no samples to judge is unknown, never pass.

The friction values are the ones the previous compiler drove its experiments with. Each approximation is listed in compile.json for the component that triggered it.

Not emitted ​

A program that uses any of these stops with a target.unsupported diagnostic naming the construct, and nothing is written: an omni base whose rolling directions do not span the plane, a steering base whose chassis declares no kingpin, a scene entity with ref, a scene entity declared movable (is_static = false: an entity states no mass to move it with), a Scenario whose ref is not empty, a joint check on a part without a moving joint, a component named like a link the target adds: base_footprint, base_link, a declared ground contact's <link>_contact_<n> or a steered wheel's knuckle <wheel>_steer, and a scene entity named like another model of the world: the robot, or ground_plane when the scenario has a floor.

The ros-mujoco-nav2 target ​

The second target keeps everything above that is ROS: the robot description (robot/robot.urdf, with a <mujoco> compiler block MuJoCo's URDF reader takes and none of Gazebo's blocks), the controllers, the navigation parameters, the map, the task files and the runtime, and swaps the simulator. Its world/ holds mujoco.json instead of an SDF and a bridge: the ground, the scene entities (each a body <name>::link, so that no entity name can meet a link's in MuJoCo's single namespace), the actuators on the wheel and kingpin joints, the wheels' contact friction, the sensors with the topics they publish on, and the spawn pose. Each body weighs what the library's inertial states: the compiler block stops MuJoCo from inferring a mass from a link's collision shapes, so a link without an inertial (the root, a ground contact's) weighs only MuJoCo's 1 g bound. runtime/run_mujoco_sim.py loads the description and that scene, steps the physics paced to the wall clock, publishes /clock, and speaks to ros2_control through its topic-based hardware (/mujoco/joint_states, /mujoco/joint_commands). It publishes the robot's pose on /model/<robot>/pose and every sensor on the same topics as the Gazebo target, computed from the physics state: lasers and range finders cast rays (the robot never sees itself, and the floor never returns), cameras render offscreen (OSMesa by default, MUJOCO_GL=egl with a GPU), an IMU reads the body's motion, a bumper reads the contacts. The launch takes the same arguments; headless has no effect.

MuJoCo's contact friction is isotropic, so it cannot yet stand in for a mecanum or omni wheel, which rolls freely along its axle: a base on such wheels is refused with target.unsupported and compiles for ros-gz-nav2 instead. A part that declares no collision box is refused too: the Gazebo target collides such a part through its visual mesh, which the library ships as Collada, and MuJoCo reads meshes only as STL, OBJ or MSH. The world's gravity and ground plane are the program's, as in Gazebo, and so is the refusals of a base environment other than "empty" and of an entity declared movable. Its own stand-ins, declared in compile.json:

ConstructEmittedReason
A wheelA sphere contact of the wheel's radius with isotropic friction 1, 0.01 for a wheel that does not rollMuJoCo's contact friction is isotropic; a rolling wheel grips, a caster slides
A ground contact a part declaresA sphere contact of its radius on the Gazebo target's fixed link, with isotropic friction 0.01Like a caster, a support slides in every direction
The driveA velocity actuator of gain 0.5 N m s/rad on each driven wheel, a position actuator of gains 50 N m/rad and 2 N m s/rad on each kingpinThe library does not state the drives' response
A range finderIts reading from the cone's nearest return, the floor never returningA pulse glancing off the floor does not echo; the rays skip it
A skid-steer baseA base that turns in place at about a third of the commanded rate while its wheel odometry reports the commanded turnMuJoCo's isotropic friction resists a wheel dragged across its rolling direction as much as it grips along it

The test image is robotdsl/ros-mujoco-nav2:jazzy, built from docker/ros-mujoco-nav2/jazzy/Dockerfile.
