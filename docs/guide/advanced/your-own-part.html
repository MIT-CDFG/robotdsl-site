Adding your own part ​

A part the catalog lacks goes into a library of your own: a directory next to your program, named with a second --library.

text
my_parts/
├── library.yaml
└── parts/
    └── lidar_ld06/
        ├── component.yaml
        └── assets/model.dae
yaml
# my_parts/library.yaml
name: my_parts
parts:
  - lidar_ld06

A sensor ​

This is the demo robot's lidar:

yaml
schema_version: 1
id: lidar_ld06                     # the directory's name
category: sensor
description: LDRobot LD06 2D lidar.
visual:
  file: assets/model.dae
  xyz: [0.0033, -0.0001, -0.012]   # where the mesh sits in the part frame
  rpy: [0, 0, -1.5708]
collision:
  type: box
  size: [0.038, 0.038, 0.033]
  origin_xyz: [0, 0, 0.0165]
inertial:
  mass: 0.0824982
  origin_xyz: [-0.000109908, -0.003282139, 0.01204194]
  inertia: {ixx: 3.621828e-05, ixy: 0, ixz: 0, iyy: 4.345764e-05, iyz: 0, izz: 4.733319e-05}
  source: cad_measured
connectors:
  mount:
    pos: [0.0033, -0.0001, -0.024]
    dir: [0, 0, 1]
    up: [0, -1, 0]
profiles:
  Lidar:
    mounts: {default: mount}

Every length is in metres and every vector is [x, y, z] in the part's own frame: +x forward, +y left, +z up. A sensor looks along its own +x.

The fields that matter most ​

collision. A box that stands in for the mesh. Leave it out and the Gazebo target collides through the mesh while the footprint rule warns that it cannot bound the robot; the MuJoCo target refuses the part, since it cannot read the mesh. Declare one.

inertial. Mass in kilograms, centre of mass, and all six inertia terms. source says where the numbers came from: measured, datasheet, cad_measured, estimated or placeholder. An estimate or a placeholder also needs a basis, a sentence saying how it was chosen, such as solid cylinder at 270 kg/m^3. The compiler never makes a mass up.

connectors. The points where the part mates. pos is the point and dir the mating axis; when two parts mate, their points meet and their directions face each other. up fixes the roll about dir for a part whose orientation matters, such as a camera or a lidar.

profiles. The component types the part can be used as, each mapping the type's logical mounts to connectors. A sensor or a wheel maps default.

A wheel ​

A wheel states its size, and the connector it mates by carries the axle joint:

yaml
schema_version: 1
id: standard_80
category: wheel
description: Plain rubber wheel, radius 0.04 m.
visual: {file: assets/model.dae, xyz: [0, 0, 0], rpy: [0, 0, 0]}
wheel: {radius: 0.04, width: 0.03}
inertial:
  mass: 0.1
  origin_xyz: [0, 0, 0]
  inertia: {ixx: 0.00005, ixy: 0, ixz: 0, iyy: 0.00005, iyz: 0, izz: 0.00008}
  source: estimated
  basis: solid cylinder
connectors:
  mount: {pos: [0, 0, 0], dir: [0, 0, 1], joint: {type: continuous, axis: [0, 0, 1]}}
profiles:
  Standard: {mounts: {default: mount}}

A wheel declares no collision: the targets derive its rolling contact from radius and width.

A range finder ​

A Range part, an infrared or time-of-flight distance sensor, states what it measures in a range block, from its datasheet. Its frame is its emitter: the origin where the beam starts, +x along it.

yaml
schema_version: 1
id: tof_vl53l1x
category: sensor
description: A time-of-flight distance sensor on a small carrier board; it looks along its +x axis.
visual: {file: assets/model.dae, xyz: [-0.021, 0, 0], rpy: [0, 0, 0]}
collision: {type: box, size: [0.003, 0.018, 0.013], origin_xyz: [-0.0015, 0, 0]}
inertial:
  mass: 0.0005
  origin_xyz: [-0.0015, 0, 0]
  inertia: {ixx: 2.1e-08, ixy: 0, ixz: 0, iyy: 7.4e-09, iyz: 0, izz: 1.4e-08}
  source: estimated
  basis: board at 0.5 g
range: {min_m: 0.04, max_m: 4.0, field_of_view_rad: 0.47, rate_hz: 50}
connectors:
  mount: {pos: [-0.0015, 0, -0.0065], dir: [0, 0, -1], up: [1, 0, 0]}
profiles:
  Range: {mounts: {default: mount}}

A sensor that says only whether something is within one distance states it as both min_m and max_m. Sensors says what the targets do with these numbers.

A chassis ​

A chassis declares a connector for every mount of its chassis type and maps them in its profile. A two-wheel base resting on a skid molded into its body declares the skid under contacts, so that the statics rule counts it and the simulators have it:

yaml
connectors:
  wheel_mount_left:  {pos: [0, 0.12, -0.02], dir: [0, 1, 0]}
  wheel_mount_right: {pos: [0, -0.12, -0.02], dir: [0, -1, 0]}
  top_mount:         {pos: [0, 0, 0.05], dir: [0, 0, 1], up: [1, 0, 0]}
contacts:
  - {xyz: [-0.15, 0, -0.035], radius: 0.025, note: molded skid under the tail}
profiles:
  Diff_two_caster:
    mounts: {left_wheel: wheel_mount_left, right_wheel: wheel_mount_right, middle_top: top_mount}

Put the chassis' mass where it really is. A base whose centre of mass sits right over its axle leaves its caster unloaded and tips onto its nose when it brakes. The statics rule catches a centre of mass on or outside the edge of the ground contacts, but not one a few millimetres inside it.

A steered wheel mount also states its kingpin, steering: {axis: [0, 0, 1], max_angle_rad: 0.6}; see Drive types.

Checking it ​

A part is checked when a library is loaded. Run --check with a program that uses it:

sh
mobiledsl compile robot.core robot.world robot.task \
  --library path/to/catalog --library my_parts --check

A problem points into component.yaml: a missing field, a vector that is not unit length, an inertia that no body could have, a mesh that is not there. A part with a problem is left out of the library with a warning, and a program that names it gets an error repeating why.

Today a part is one rigid body with its connectors. A part with links and joints of its own, such as an arm or a pan-tilt mount, cannot be declared yet.

The library format specifies every field and every diagnostic.
