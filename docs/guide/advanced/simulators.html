Gazebo or MuJoCo ​

Both targets emit the same robot description, controllers, Nav2 settings, map, task and runtime. They differ in the simulator underneath.

sh
mobiledsl compile ... --target ros-gz-nav2 --output build
mobiledsl compile ... --target ros-mujoco-nav2 --output build_mujoco

What each runs ​

Both publish the same topics, including the robot's ground-truth pose on /model/<robot>/pose, so the same task runner judges both.

What each refuses ​

A target refuses what it cannot simulate, at compile time, instead of writing something that runs wrong.

Constructros-gz-nav2ros-mujoco-nav2
A mecanum or omni baseSimulatedRefused: MuJoCo's contact friction is the same in every direction, so a wheel cannot slide freely along its rollers
A part without a collision boxCollides through its visual meshRefused: MuJoCo cannot read the Collada mesh
A movable entity (is_static = false)RefusedRefused
A base environment other than "empty"RefusedRefused
A scene entity given by refRefusedRefused

Where they differ in behaviour ​

  • Skid-steer turns. In MuJoCo a skid-steer base turns in place at about a third of the commanded rate, while its wheel odometry reports the full turn.
  • Contacts. Gazebo gives each kind of wheel its own friction model, anisotropic where the wheel slides one way. MuJoCo gives a rolling wheel a grip of 1 and a caster or skid 0.01, in every direction.
  • The drive. MuJoCo drives each wheel through a velocity actuator whose gain the target chooses, since the library does not state the motors' response.

Each of these is declared in compile.json.

Which to use ​

Use ros-gz-nav2 for any base, and for parts that declare no collision box. Use ros-mujoco-nav2 for a base on standard wheels when you want a second simulator's opinion of the same program: a run that passes in one and fails in the other points at something the program leaves to a simulator's defaults.

The output contract specifies both targets' files in full.
