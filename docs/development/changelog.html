Changelog ​

All notable changes to this project are documented here.

[Unreleased] ​

Changed ​

  • The demo program and the parts of the documentation's example robots live in examples/ (examples/demo, examples/library) instead of among the test fixtures; the parts only the tests use (the other drive and sensor types) stay in tests/library/fixtures/test_parts, and the tests load both libraries. The tests, the getting-started guide and the README read the same four demo files, so the guide's copy can no longer drift from the tests' (it had: the tests still stated is_static on the demo's obstacles).

  • The documentation is a VitePress site in docs/, laid out as a guide (Introduction, Basics, Advanced), the reference specification, and the development notes, after Lucide's documentation. The guide is new: a first program from source to a run, one page per file and per concern, and the deeper pages on parts, drive types, sensors, validation, judging a run and the two simulators, with the language highlighted. Every example in it compiles, and the getting-started run was carried out as written. The generated vocabulary page also stops splitting a row at a choice's |. The site is published inside the project site at https://mit-cdfg.github.io/robotdsl-site/docs/, in the site's type and colour, and the site's own page is its home.

  • A scene entity stays in place unless the program says otherwise: is_static defaults to true, and both targets refuse an entity declared movable (is_static = false), since an entity states no mass to move it with. The Gazebo target gave a movable entity SDF's default inertial, 1 kg and a unit inertia, and a Marker without the flag, having no collision, fell through the floor; the evaluator also judges contact against each entity's declared pose. All 145 entities in robotdsl-experiment's 53 worlds already declare is_static = true, so their output does not change.

  • Where each world name is and what each entity covers seen from above are analysis facts, which the map, the mission and the evaluator read instead of each reading the world on its own. task/mission.json holds every goal and every entity under locations (it held goals); an entity in task/evaluation.json carries the region it covers, a circle or a convex polygon, in place of its shape, pose and size; compile.json lists locations in place of goal_poses. A Marker's collision default is settled once, in lowering.

Removed ​

  • The phases root_validation, elaboration and normalization, which no code ran: the JSON result listed them as not_run even for a clean compile. The compiler failure domain and the compiler_failed status, which nothing produced, are gone from the diagnostics specification, and its examples are now real output of the current language.

Fixed ​

  • A third review found places where a program compiled but its run failed or was judged wrongly. An entity's region follows its full pose: a cylinder lying on its side was a circle at its centre, so the map left its length free and a robot parked on it was judged 0.5 m clear. Navigate and GoalReached reach an entity as well as a goal, as the vocabulary says: the mission held only goals and the run failed on an entity. A goal on an entity widens the map like any other: a goal 20 m away sat outside a map 9 m wide. A task halted before Nav2 accepted its goal cancels it once it is accepted: the cancel was dropped and the goal ran on; the runtime now waits for canceled goals to stop and names any that did not. The output is written by replacing each file, never through a link, and a linked directory in it is refused: an output robot.urdf linked to the program's .core overwrote the source. --warnings-as-errors blocks when the warning is found, so nothing is written; it failed the compile after 30 files had been. An empty Sequence, Fallback or Parallel and a task without a node are refused (type.children_required) instead of being refused by the runtime, and a number beyond a float, such as 1e999, is syntax.number_out_of_range instead of a crash while drawing the map.
  • What a run is judged against, what navigation plans with, and what the simulators are given agree with the robot the simulators collide (reported in a second review). The evaluator measures each ground contact a part declares as part of it and each wheel as the circle of its sphere: a skid reaching 1 cm into an obstacle behind the chassis was judged 9.5 cm clear, with no contact. Nav2's footprint covers the wheel spheres: a two-wheel base planned 0.27 m wide collided 0.32 m wide. MuJoCo gets each scene entity as a body of its own, <name>::link: an obstacle named like a link compiled and the node stopped on repeated name; the Gazebo target, whose world holds the robot and the floor as models, refuses an entity named like either. And the library checks an inertia tensor by its principal moments: a chassis with ixy = 0.02 loaded and MuJoCo refused it (inertia must have positive eigenvalues); the 385 parts of the component catalog still load.
  • A ground contact a part declares (contacts) is modelled consistently (reported in review). Its link no longer adds mass in MuJoCo, which had inferred one from the sphere, 65 g for the test library's skid and 4.2 kg for a 0.1 m ball: the description's compiler block sets inertiafromgeom="false", so each body weighs what the library states. The footprint reaches around a contact that sticks out past the chassis, where it had stayed at the box (a skid at x = -0.5 m left it at -0.17). A contact that reaches below the wheels' plane fails statics.mass_inside_the_wheel_contacts instead of being counted as raised: 0.1 m below the wheels the rule passed and the base came to rest tipped 33 degrees in MuJoCo. And a component named like a link the target adds, a ground contact's <link>_contact_<n> or a steered wheel's knuckle <wheel>_steer, is refused as base_link already was: two links of one name compiled and MuJoCo then refused the description.
  • The ros-mujoco-nav2 target builds the world the program states. The node ran every world with MuJoCo's own gravity and a ground plane, and held every entity in place: a world in free fall without a floor ran as the demo room, and a movable obstacle became a fixed one. The scene now carries the world's gravity and whether it has a ground plane; an entity declared movable is refused, as is a base environment other than "empty".
  • The MuJoCo node's IMU reads linear acceleration. MuJoCo fills body accelerations only when a model has acceleration sensors, and the node computes its sensors itself, so a body pushed at 3 m/s^2 read zero while gravity was added by hand. The node now fills them before reading, and a container check reads an IMU at rest and pushed against the known answer.
  • A ground contact a part declares under contacts is simulated: both targets give it a sphere collision on a fixed link of its own that slides like a caster. The statics rule counted such a skid as a support while neither simulator had it, so a two-wheel base on a molded skid passed the rule and then rested tipped 10 degrees onto its chassis in Gazebo and MuJoCo alike. The motion checks now also require every base to rest level.
  • The ros-mujoco-nav2 target refuses a part that declares no collision box. The robot description collides such a part through its Collada visual mesh, which MuJoCo cannot read, so the program compiled and then stopped at start-up. In the format-1 catalog 36 of 73 chassis and 7 of 9 sensors declare no collision box.

Added ​

  • A range finder that measures with light, Range, for infrared triangulation and time-of-flight distance sensors (issue #1), which had only Ultrasonic to be declared as. A Range part states what it measures in a range block, min_m, max_m, field_of_view_rad and rate_hz, since the products it stands for reach from 0.6 m to 4 m in cones of different widths and no default could stand in; an Ultrasonic part may state one too. Equal limits make a fixed-distance sensor, which reports -inf or +inf as sensor_msgs/Range defines it. Both targets simulate it as a cone of beams whose nearest return is the reading on /range, INFRARED, and, unlike an ultrasonic sensor's, its floor returns are kept: light comes back from the floor. The advisory rule sensing.range_clears_the_ground warns when a Range sensor's cone meets the ground within its range, where the costmaps would mark the floor as an obstacle; a rule can now be advisory, its fail a warning; the summary line counts it (1 advised against) and its entry in the JSON result says "advisory": true. Checked in both simulators: a narrow infrared sensor takes the differential robot to its goal, and a level time-of-flight sensor 0.12 m up reads the floor 0.49 m away, where the rule says its cone meets it, and the local costmap marks an obstacle there; a fixed-distance sensor answers +inf in an open room and -inf to a bar within its 10 cm.

  • provenance ignores the keys it does not know. A library may keep what its own tools need with the part (a price, how many a purchase supplies, a maker's catalog number) without the compiler knowing them; the four keys the compiler reads are checked as before. Everywhere else a declaration still has no free-form fields.

  • Add architecture, language, and developer onboarding documentation.

  • Add the mobiledsl package skeleton, the import-boundary tests that enforce the documented dependency direction, and CI.

  • Add the shared diagnostic, span, and source-map types (support/), taken from MobileDSL-Compiler.

  • Add the frontend for the four source forms (.core, .world, .task, .eval): one grammar with a start rule per form, a source-anchored syntax tree, and syntax diagnostics. Compared with the previous compiler, component types, task node types and check names are ordinary names resolved later instead of grammar keywords; poses and vectors are tuples instead of strings; references are @world/goal instead of "@world/goal"; # comments are gone.

  • Render diagnostics in the terminal the way rustc and ruff do: a heading with the code, an excerpt with the spans underlined, help and note lines, and color when writing to a terminal.

  • Add the component library loader: library.yaml plus parts/<id>/component.yaml, read as spanned YAML so that every problem points into the library file. Compared with the previous compiler's part.yaml: model is visual, geometry is wheel, the joint moves into the connector that creates it, and catalog images are no longer checked by the compiler.

  • Add the standard vocabulary (semantic/model/vocabulary.py): the component types, entity types, task nodes and checks a program may name, with their parameters. The specification page is generated from it. The task vocabulary names what the robot must do (Navigate, Spin, Wait, ...) and nothing about how a navigation stack does it.

  • Add lowering (semantic/lower.py): resolve the four syntax trees against the vocabulary and the loaded libraries into one typed program, reporting every unknown name, ill-typed argument, unresolved reference and structural problem in one pass, with suggestions for near misses.

  • Add analysis (semantic/analysis/): mate each component onto the chassis connector its glue names, and derive placements, wheel contacts, mass and centre of mass, the footprint from declared collision shapes, drive facts, sensors, goal poses and task use. A glue that matches no connector is a fact (unplaced), not a guess.

  • Add validation (validation/): rules that answer pass, fail, unknown or not applicable over the facts, with evidence and findings that point at the program. Standard rules cover glue-to-connector matching, connector occupancy, wheel mounts and classes, horizontal axles, a common contact plane, footprint coverage, and whether the task's Spin and Strafe suit the base. The rule table is rendered into the specification.

  • Add the driver and the mobiledsl compile command: the four files as arguments, --library directories, --check, --json, --warnings-as-errors and --color. Diagnostics and a summary go to stderr, colored on a terminal; the structured result goes to stdout. No target exists yet, so --target reports that.

  • Specify the grammar, the vocabulary, the component library format, the validation rules, the diagnostic contract, and the output contract.

  • Add the target interface (targets/api.py): a target turns the program and its facts into exact file bytes plus copies of library assets, declares every stand-in it makes as an approximation, and refuses what it cannot realize with a target.unsupported diagnostic that points at the source.

  • Add the first target, ros-gz-nav2, composed of a Gazebo adapter (URDF links, joints and inertials from the analysis placements, meshes copied from the libraries, sphere wheel contacts with class-based friction, simulated laser, IMU and camera sensors, a ground-truth pose publisher, the world SDF), a ROS 2 adapter (ros2_control interfaces, the mecanum and differential drive controllers fed by the analysis kinematics, one /cmd_velTwistStamped entry point) and the composition (topic bridge, mission file, bringup.launch.py). Skid-steer, tricycle, Ackermann and omni bases are refused until a controller is bound and verified.

  • Add the output write phase to the driver: --target NAME --output DIR writes one directory, refuses an output that is, holds or sits inside a source or library, overwrites only its own files, and adds compile.json with the facts, validation results, approximations and provenance.

  • Add the in-image test tiers: pytest -m container checks the emitted files with the target's own tools, pytest -m simulation launches the directory and judges motion by the simulator's poses.

  • Add navigation and task execution to ros-gz-nav2: nav/nav2.base.yaml (the target's Nav2 policy) and nav/nav2.robot.yaml (footprint, inflation, the path follower for the base's kinematics, the laser the costmaps watch), task/behavior_tree.xml (the task in BehaviorTree.CPP layout over the vocabulary), and runtime/ (a task executor that binds each node to Nav2 actions, /cmd_vel, odometry and TF, and writes run/task_result.json). The launch starts Nav2 after the drive controller and the task after Nav2, and ends when the task ends. The simulation tier runs the whole demo and checks the task result against the simulator's pose at the goal.

  • Execute the .eval file: the target emits task/evaluation.json (the checks and the planar collision shapes of parts and entities), the runtime records the simulator's pose and the joint states while the task runs, and run/evaluation.json gives three verdicts from independent evidence: the task's own status, the physical outcome from ground truth (goal reached within twice the controller's tolerance, no obstacle touched), and every check with the value it was judged on. The vocabulary states what each check's bounds mean; Check_contact does not count a support surface.

  • Draw the map from the world: every obstacle is rasterized into nav/map.pgm for the map server, the global costmap gets a static layer, and a robot with a laser localizes against the map with AMCL from its spawn pose. A robot without a laser keeps the map frame pinned to odometry.

  • Bound the vocabulary to what the compiler acts on: Arm, Gripper and Tray are one Attachment type, Ultrasonic is gone until a target simulates it, and an architecture test checks that every component type, task node, check and entity type has a consumer in analysis, validation or a target.

  • Support a depth camera: simulated in Gazebo, its image and cloud bridged, and, on a robot without a laser, its cloud projected onto the scan that the costmaps and AMCL read (runtime/run_depth_scan.py).

  • Require Python 3.12, the version CI and the target image already use; the runtime payload's numpy stubs need it for type checking.

  • Name a part's profiles after the component types: a library entry lists the types the part can be used as (profiles: {Lidar: ...}), and the separate lower-case profile names are gone. The vocabulary table is Type, Category, Meaning; the chassis table names chassis and wheel types. Facts, rules and diagnostics say "chassis" and "wheel type" where they said "profile" and "class" (assembly.wheel_type_matches_chassis, name.type_not_supported).

  • Drive a Diff_drive (four-wheel skid-steer) base: the differential controller takes both wheels of a side, and each wheel's sphere contact grips along the rolling direction and slides across it.

  • Drive tricycle and Ackermann bases: a chassis declares the kingpin of a steered mount (steering: {axis, max_angle_rad}), the analysis reports which wheels drive, steer or only roll and the base's minimum turning radius, a rule asks for an upright kingpin on every steered mount, the robot description hangs steered wheels from knuckle links, the tricycle and Ackermann steering controllers are bound, and such a base plans with Smac Hybrid-A* and follows with MPPI's Ackermann model. The launch takes navigation:=false to bring up only the simulator, the robot and its drive controller.

  • Sense with a spinning lidar (Lidar3D: a 16-ring gpu_lidar whose middle ring is bridged as a planar scan and whose cloud is bridged as points) and an RGBD camera (RGBD: colour and depth images and a cloud). Every point cloud is an observation source of both costmaps (points 0.05 to 2 m above the ground); the localizer reads the first laser, else the first spinning lidar's ring, else a scan projected from the first depth or RGBD camera's cloud.

  • Sense with an ultrasonic range finder (Ultrasonic): the simulator has no such sensor, so a gpu_lidar of 9 by 9 beams fills its cone and runtime/run_range_sensor.py reports the nearest return above the floor as a sensor_msgs/msg/Range, which the costmaps' range layer marks. A robot with only range finders navigates on the known map from its spawn pose.

  • Sense with a bumper (Bumper): an ideal contact sensor on the part's collision box, bridged as ros_gz_interfaces/msg/Contacts. The task runtime records its reports, and Check_contact on a bumper is judged from them (seconds pressed, entities that pressed it) instead of from the geometry.

  • Drive omni bases (Omni_three_wheel, Omni_drive) in any layout: the analysis reads each wheel's position and rolling direction, the rule kinematics.omni_wheels_span_the_plane asks that the directions span the plane, each wheel's contact grips along its roll and slides along its axle, and the base is bound to a joint group velocity controller fed by runtime/run_omni_drive.py, which computes the wheel speeds and the odometry from the layout. ros2_controllers' omni controller models only wheels evenly spaced on a circle; the catalog's four-wheel omni bases sit on rectangles with their axles along the diagonals.

  • Prepare the targets for a second simulator: the mission and evaluation data every runtime reads move to targets/mission, the runtime files every target copies are assembled by targets/payload, the robot description can be built without Gazebo's blocks, and the simulated sensors' stand-in specifications are public.

  • A second target, ros-mujoco-nav2: MuJoCo simulates the robot through the runtime's own node (runtime/run_mujoco_sim.py, world/mujoco.json) and ros2_control's topic-based hardware; the robot description, controllers, navigation, task runtime and evaluation are the Gazebo target's. Lasers, spinning lidars and range finders cast rays, cameras render offscreen, the IMU and the bumper read the physics state. Bases on mecanum or omni wheels are refused: MuJoCo's contact friction is isotropic; for the same reason a skid-steer base turns at about a third of the commanded rate, which the target declares as an approximation. The test image is robotdsl/ros-mujoco-nav2:jazzy (docker/ros-mujoco-nav2/jazzy).

  • A statics rule, statics.mass_inside_the_wheel_contacts: the robot's centre of mass must fall strictly inside the polygon of its ground contacts, the wheels and the skids or balls a part declares under contacts (now placed into the facts), or the robot tips at rest. When the contacts lie on one line the rule is undecided and asks for the skid or a caster. Found when the demo two-wheel base, whose part declared its mass over the axle with nothing on the caster, tipped onto its nose under braking in both simulators and its depth camera saw the floor as a wall; the rule reports the margin, and points at the chassis with every contact.

  • Convert the previous compiler's schema-3 component library into this format with tools/convert-library (mobiledsl.library.convert): renamed fields, the joint moved onto the wheel's connector, profiles named after component types, meshes copied under assets/, and a report of what was dropped or left absent. The real catalog converts to 248 loadable parts out of 254; the six the loader refuses are gaps in the data (placeholder inertials without a basis, an id declared in two categories, a tricycle without a kingpin).

  • A defective part declaration no longer blocks every program that uses the library: the part is left out with a warning, and a program that names it gets a name-resolution error saying why it could not be loaded. Found when the converted catalog's four incomplete parts blocked robots built from the 248 complete ones.
