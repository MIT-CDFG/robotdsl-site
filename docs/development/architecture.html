Architecture ​

RobotDSL-Core is a Python compiler. It checks robot, world, task, and evaluation descriptions together, then generates native files for the user's robot environment. ROS, simulators, and Docker are execution or test dependencies, not compiler dependencies.

Target packages own their binding, native-input adapters, typed output models, and emitters. ros_gz_nav2 owns Gazebo–ROS integration and composes the launch plan; Gazebo and Nav2 do not import each other. Changing simulators reuses robot and task semantics and autonomy adapters; composition checks interface compatibility. Runtime helpers live with their owning adapter and execute in the target environment. Compiler code never imports those helpers or ROS/simulator SDKs.

Lowering resolves names, checks types, fills in the defaults the vocabulary states, and normalizes the syntax tree. Analysis derives facts such as geometry, mass, connectivity, where each world name is and what each entity covers, and action dataflow. Validation judges those facts without recomputing them or changing the model, and a target reads them rather than interpreting the program again: the map, the mission and the evaluator each read the world on their own once, and disagreed. Missing required facts produce diagnostics; optional unknowns remain visible. Validated values are immutable and retain their source locations.

The target binds actions and requirements to selected implementations. It checks unsupported operations and cross-file references before producing exact output bytes. The driver writes them only after planning succeeds and protects input files and unrelated output contents.

Dependency direction ​

Each compiler package imports only the packages in its row, plus support, which holds diagnostics and source locations.

PackageImports
clidriver
driverevery package below
semantic.lowerfrontend, library, semantic.model
semantic.analysissemantic.model
validationsemantic.model
targetssemantic.model
frontend, library, semantic.modelnothing

Inside targets, the simulator adapters (gazebo, mujoco) and the autonomy adapters (ros2, nav2) never import each other; a composing target (ros_gz_nav2, ros_mujoco_nav2) imports the ones it needs. The robot description is built by the Gazebo adapter and reused by the MuJoCo target without Gazebo's blocks. targets/mission (the mission and evaluation data every runtime reads) and targets/payload (the runtime files every target copies) are shared by the composing targets and imported by no adapter.

Lowering consumes the AST and already-loaded library declarations; the resolved model and its analyses do not depend on the parser. Frontend, semantic, and validation code do not import targets or perform file I/O. The driver loads source files and calls library loaders. Runtime helpers consume emitted data, not compiler models. URDF elements, plugins, topic names, and contact approximations belong in targets. Native-input adapters retain original files alongside their semantic projection.

Tests enforce import boundaries, compilation without ROS or simulator packages, and execution of generated output without the compiler checkout or installation.

Libraries and surrounding projects ​

Component and scene libraries are ordinary directories supplied explicitly at compile time. They contain declarations and local assets; they have no install step, package store, or hidden default location.

Acquisition, CAD conversion, image reconstruction, calibration, and policy training belong to external preparation tools. Original assets and official webpages stay with library source material. The experiment project owns cases, repetitions, acceptance thresholds, and aggregate scores.

Generated output ​

Typed target models supply native consumers from the same resolved facts:

  • Robot/world descriptions and their assets.
  • Controller, perception, and navigation configuration.
  • Executable task bindings, observation settings, and a launch entrypoint.
  • Diagnostics and optional inspection views, separate from execution inputs.

Each executable responsibility has one authoritative representation. Runtime-facing formats are defined separately from internal compiler models. Shared values in different native formats are derived consistently. Output contains its required resources or explicitly binds resources supplied by the user's environment; it does not depend on the compiler checkout. Runtime logs and results stay outside the output.

Simulator and autonomy bindings are separate concerns. A new target implements the same semantic contracts and verifies actuation, sensors, timing, reset, and observations. Compilation checks the declared configuration; startup and execution establish whether the robot actually works.

See Language for semantics and Developer onboarding for the development workflow.
